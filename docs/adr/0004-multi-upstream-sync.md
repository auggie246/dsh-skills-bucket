# Multi-upstream sync

The bundle syncs from more than one upstream: `upstream.lock.json` holds a `sources` array, one sync source per upstream repo, each with its own release-tag pin, layout (`flat` for `skills/<name>/SKILL.md` trees like DietrichGebert/ponytail, `categories` for category-nested trees like mattpocock/skills), and optional patch repo. One run re-syncs every source at its pin; `--repo` targets one; `--add-source` records a new one. A skill name claimed by two sources is a hard error — cross-repo duplicates are ambiguous, so sync refuses to guess. At install time the sync folds multi-line YAML block-scalar descriptions (`description: >`) into single lines, because the skill registry's frontmatter parser reads flat scalars only; a `|` literal block fails the sync instead of being folded silently. The rejected alternatives: a second one-off sync script per upstream (two copies of the pull-patch-flatten pipeline that drift), and hand-vendoring the ponytail skills without a pin (provenance lives nowhere, updates stop being reproducible). Trade-offs: the lock format changed from a single `upstream` block to `sources[]` (the script upgrades a v1 lock in place on first run), and ponytail ships with no overlay patches because its skills contain no ask-the-user gates to reroute.
